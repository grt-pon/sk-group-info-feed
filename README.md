# 古紙情報収集パイプライン(SKグループ情報フィード バックエンド)

古紙・廃棄物業界の情報を収集し、要約・カテゴリ分類してSupabase(共有DB)に保存するバックエンド。
「情報源ごとに収集の仕組みを1つ作り、出てきたものを後からカテゴリ分けする」という方針で作っている。
④企画立案エージェント(別プロジェクト)とは完全に独立しており、このフォルダ配下のみで完結する。

## セットアップ

```bash
npm install
cp .env.example .env
```

`.env` に以下を設定する。

- `ANTHROPIC_API_KEY`: Claude(要約・分類に使用)
- `TAVILY_API_KEY`: Tavily(キーワード監視に使用)
- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`: Supabase(保存先。他の人も同じデータを見られる共有DB)

保存先は `src/lib/store.js` が優先順位(Supabase > Firestore > ローカルファイル`data/items.json`)で自動選択する。Supabaseを使わない場合の代替として Firestore(`FIRESTORE_PROJECT_ID` / `GOOGLE_APPLICATION_CREDENTIALS`)も残しているが、現状はSupabaseを使う方針。

### Supabaseのセットアップ

1. https://supabase.com/ でプロジェクトを新規作成する(既存の秘書ツール等とは別の、このプロジェクト専用のプロジェクトを作る)
2. 作成したプロジェクトの「SQL Editor」で `supabase-schema.sql` の内容を実行し、`items` テーブルを作る
3. プロジェクトの「Settings > API」から `Project URL` と `service_role` キー(`anon`キーではない点に注意。サーバー側からの書き込みに使うため)を取得し、`.env` に設定する
4. 他の人にも見てもらう場合は、Supabaseプロジェクトに「Settings > Team」からメンバーとして招待すると、Table Editorから直接データを見られる

## 実行

```bash
npm run collect
```

`scripts/runOnce.js` が全情報源を順番に実行する。1つの情報源が失敗しても他の情報源の収集は続行する。

## ローカルでフロントエンドを見る

```bash
npm run serve
```

http://localhost:3000 で、保存先(Supabase等)のデータをSKグループ情報フィードのデザインで表示するページが起動する。「使える/不要」のボタンは各記事に`reactions`として記録されるが、一覧の表示には影響しない(方針通り)。Supabaseを共有していれば、他の人が別のPCで同じ`npm run serve`を実行しても同じデータが見える。

## 設計上の決定事項

- **全文を保存しない**:元記事の全文は取得・保存せず、Claudeが生成した独自要約と元記事へのリンクのみを保持する(著作権配慮)。
- **重複排除は `sourceUrl + publishedAt`**:同じページが日付を変えて繰り返し「更新しました」と告知されるケース(古紙再生促進センター、日本製紙連合会の統計更新など)があるため、URLだけでなく更新日も見て別記事かどうかを判定する。
- **カテゴリ分類はルール(キーワード)+ Claude判定のハイブリッド**:`src/config/categoryRules.js` のキーワードで一次判定し、Claudeが最終判断する。
- **部署タグは付けない**:カテゴリの取捨選択は各利用者が「じぶんの情報をみる」で自分で行う前提のため、記事に部署を自動で紐付ける処理は持たない。
- **反応(要る/要らない)は記事の表示可否に直接影響させない**:個々の記事の採否を誰か一人(または多数決)が決める仕組みにはせず、反応は蓄積してカテゴリルール・情報源の見直し材料としてのみ使う想定(この蓄積・分析の仕組み自体は未実装)。
- **一次情報の自動判定はドメインだけで信用しない**:循環経済新聞のダイジェストから一次情報を検索する際、`.go.jp`等のドメインだけで判定すると「たまたま同じ分野の無関係な文書」を誤って採用してしまう事例があった(例:企業の総会案内に内閣府の資料が紐づく)。そのため候補が見つかった後、Claudeで内容が実際に一致するか検証してから採用する(`isMatchingPrimarySource`)。

| 情報源 | 状態 | 備考 |
|---|---|---|
| 古紙再生促進センター | 実装済み | `src/collectors/direct/prpc.js`。実サイト構造で動作確認済み |
| 日本製紙連合会 | 実装済み | `src/collectors/direct/jpa.js`。実サイト構造で動作確認済み |
| 関東製紙原料直納商工組合 | 実装済み | `src/collectors/direct/kantoshoso.js`。PDFリンクの取得のみ、中身は未解析 |
| 一般キーワード監視(Tavily) | 実装済み | `src/collectors/keyword/tavilyMonitor.js`。`topic:"general"`を使用(`"news"`だと専門分野の記事を拾えなかった)。古紙ジャーナル・循環経済新聞のドメインは除外設定済み |
| 経済産業省(資源循環経済小委員会) | 実装済み | `src/collectors/direct/meti.js`。既定のUser-Agentだと403になるためブラウザ相当のUser-Agentを付与している。古紙・パルプの案内ページは更新のない静的ページだったため、審議会ページに切り替えた |
| 循環経済新聞 | 実装済み | `src/collectors/keyword/junkanKeizaiShimbun.js`。トップページのダイジェストは実際には`<np-list>`要素が`https://www.nippo.co.jp/json/news-paper/jk{年}.json`を取得しているだけと判明し、ヘッドレスブラウザ不要で直接取得できた(Playwrightは検証したが結局使っていない)。ダイジェストの文章は使わず、見出し・発信元組織名を手がかりに一次情報をTavilyで検索し、Claudeで内容一致を検証してから採用する(共通ロジックは`src/lib/primarySourceTracer.js`) |
| 環境省(資源循環) | 実装済み | `src/collectors/direct/env.js`。`/press/recycle/index.html`という「資源循環」カテゴリに絞られた報道発表一覧があり、絞り込み不要でそのまま使える |
| 宮城県 | 実装済み | `src/collectors/direct/miyagi.js`。県庁全体のお知らせ一覧のため`isRelevantTopic`によるキーワードフィルタを通す(実測で100件中1件程度がヒット) |
| 仙台市 | 実装済み | `src/collectors/direct/sendai.js`。市役所全体の記者発表資料(当月分ページ)のため同様にキーワードフィルタを通す |
| 日経新聞(地域面・東北) | 実装済み | `src/collectors/keyword/nikkeiLocal.js`。見出しは無料で見えるが本文は有料のため、循環経済新聞と同じ「見出しから一次情報を辿る」方式(`primarySourceTracer.js`)を流用。プレスリリースが先行し報道が後追いすることがあるため検索期間を365日と長めに設定 |
| 財務省貿易統計 | 保留 | HSコード指定の検索が必要な作りで、単純なページ取得では数値に辿り着けない |
| 全国製紙原料商工組合連合会 | 保留 | トップページ・「業界情報・広告」ページとも自社発信の「お知らせ一覧」が存在しない。関東以外の地域組合(神奈川・近畿・東京・中部・大阪)も調査したが、画像でのデータ公開/古紙再生促進センターのデータ転載のみ/更新停止/サイト不明のいずれかで追加する価値なしと判断 |
| 古紙ジャーナル | 保留 | 購読部署外への配信が利用規約(第9条・第12条)に抵触する可能性があり、社への確認待ち |
| 資源新報 | 対象外 | サイトの更新が確認できず候補から除外 |

## 未実装・今後の課題

- 財務省貿易統計・全国製紙原料商工組合連合会の収集経路の確定
- 直接収集系(prpc/jpa/kantoshoso/meti)は現状タイトルのみを本文代わりにClaudeへ渡しており、リンク先本文を取得すれば要約精度が上がる
- 反応(要る/要らない)データを集計してカテゴリルール・情報源の調整に使う仕組み
- 定期実行の仕組み(現状は `npm run collect` を手動実行するのみ)
- Tavilyの`topic:"general"`は関連性は高いが「新着」である保証が弱い(常設ページも混ざる)。新着性と関連性を両立する検索方法は未解決
